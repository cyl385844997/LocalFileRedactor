# LocalFileRedactor（本地文件脱敏工具）

一个**完全离线**的文件脱敏工具：把文档中的手机号、身份证号、银行卡号、邮箱、IP 等敏感信息，
**不可逆地**替换为占位符，输出到新文件。**绝不联网、绝不上传、绝不覆盖原文件。**

> ⚠️ 当前状态：**全部单元测试 732 passed, 0 xfailed**。
> **docx 已全通**：正文段落（跨 run、换行符、制表符）、超链接（含 `mailto:` 目标）、
> 表格（含合并单元格与嵌套表）、页眉页脚（含首页/ 偶数页）、批注、
> 文本框（含嵌套）、脚注、尾注。
> **文本型 PDF 已通到 P3b**：真 redaction（无文本层明确报错）、
> 表格识别分级（P2）、**元数据清洗**（`/Info` 六字段 + XMP，P3）、
> **5 处结构藏身处**（书签/注释/链接/内嵌文件/表单域，P3b）。
> **xlsx P2/P3 已实现**：14 类容器（v0.4.0）+ custom.xml / 数组公式（v0.5.0）。
> pptx / OCR / GUI 尚未实现。详见下方「已知限制」与「路线图」。

---

## 这个工具解决什么问题

把一份含敏感信息的文件交给 AI 分析、或交给第三方处理之前，先把敏感信息抹掉。
抹得干净、且**不可逆**——不是画个黑框盖住，而是把底层字符真正删掉。

## 核心承诺

| 承诺 | 实现方式 |
|---|---|
| **绝不联网** | 依赖里无任何网络库；测试 `TestOfflineGuarantee` 扫描源码禁止 `requests`/`urllib`/`socket` 等导入 |
| **绝不覆盖原文件** | 源文件只读打开；输出路径与源路径相同则直接拒绝；输出已存在默认拒绝 |
| **不可逆脱敏** | PDF 走 PyMuPDF 真正的 `add_redact_annot + apply_redactions`（P3）；其余格式直接改写文本 |
| **报告零敏感内容** | 报告只记录规则名 + 命中次数 + 位置（页/段/行），**不记录任何原文**；不生成任何映射文件 |
| **规则加载失败即中止** | YAML 语法错 / 正则编译错 → 报错退出并指明**行号**，绝不静默跳过某条规则 |
| **部分未处理必须可见** | 因结构复杂而跳过的段落会在报告中单列"需人工复核"，不会藏在"成功"里 |

## 能力边界（重要，请先读）

**能做**（纯正则 + 校验位 + 字典）：

- 手机号、18 位身份证号（带校验位验证）、银行卡号（带 Luhn 校验）、邮箱、IPv4 / IPv6
- 校验位验证能显著降低误报：18 位设备编号不会被误判为身份证

**不能做**（本工具不覆盖）：

- ❌ **人名**（张三、李四）——纯正则做不到，需 NER 模型
- ❌ **地址**（XX 路 XX 号）
- ❌ **单位名**（XX 有限公司）
- ❌ **车牌号、社保号、mac 地址**（尚未内置规则，可自行在 YAML 里加）
- ❌ **间接识别**（如"张工"这种称谓）

如果你需要识别中文人名/地址/单位名，**本工具不能替代人工审查**。
这一点会写进 README 免责声明，也是开源时必须诚实说明的部分。

## 已知限制（Known Limitations）

### 自定义词库

- **词库条目的粒度决定它会连带吞掉什么**（重要，最容易踩）
  命中消解按 `start` 升序先到先得，因此**词库条目的起点更靠前时，
  会吃掉起点更靠后的内置正则命中**，且被吃掉的正则优先级再高也没用。

  实测：词库条目 `联系人张三13800138000` 会让整句变成 `[整句]`，
  里面的手机号 `13800138000` **不会**单独脱敏。

  同一起点冲突时则是内置正则胜出（词库排在规则列表末尾，
  拿到的优先级是最低值）。所以：

  | 场景 | 谁赢 |
  |---|---|
  | 词库词与正则命中**同一起点** | 内置正则 |
  | 词库词起点**更靠前** | 词库（连带吞掉正则） |

  → **词条要写得精确**。宁可写 `'张三'`、`'13800138000'` 两条细词，
  不要写 `'联系人张三13800138000'` 这种整句。

### PDF

- **扫描件（无文本层）直接报错，不做 OCR**
  PDF 图像里的字取不出来，本工具**不做 OCR**，宁可报错让你人工处理，
  也不产出"看起来脱敏了、实际原文还在图里"的文件。请先 OCR 成可搜索
  PDF 再处理。
- **加密 PDF 不做密码交互**：无密码加密可直接处理；需要密码的会明确报错。
- **表格行列号只给有框线的表格**（P2，**有意的产品级降级**）
  PDF 规范没有表格概念，本工具用 `find_tables()` 还原行列。
  **无框线的表格（三线表、纯文本对齐）不给行列号**，位置标签退回
  "页码 + 命中矩形坐标"。这是**刻意的取舍**，不是缺陷：

  - `text` 策略虽能"识别"无框线表格，但**行结构不可信**：
    实测 4 行被拆成 7 行，且行框高度不一、互相交叠 ——
    按 `extract()` 看偶数行是空的，按 `row.bbox` 看每行都有字，
    **两个口径给出不同的行号**，用户无从判断该信哪个。
  - 更关键的是**无法区分表格与列表**：实测下列非表格全部满足
    "有数值列 / 文本短 / 无句读 / 首行像表头"四条判据 ——
    目录页（`第一章 项目概况 1`）、编号列表（`1 项目概况`）、
    参数清单（`扬程 12.5`）、联系方式块（`电话 13800138000`）。

  给一个"看似精确、实际是错的"行列号，比不给更糟：用户不会去核对。
  故**宁可少给信息，也不给错信息**——与 docx 里"域代码段落跳过"
  是同一种判断。脱敏本身**不受任何影响**。

- **`find_tables()` 的原生提示已被静音**（P2 修复，勿改回纯 fd 重定向）
  `find_tables()` 首次调用时会往 **stdout** 打一行
  `Consider using the pymupdf_layout package...`。它**写的是 stdout
  不是 stderr**，且**每进程只打印一次**（与调用次数/页数无关）。

  静音由 `_silence_native_noise()` 完成，三条实测结论
  （`.verify/probe_p2/silence/`，勿凭直觉改）：

  1. 提示经 **Python 的 `sys.stdout`** 写出，先进**缓冲区**；
     纯 `dup2` 只改 fd 指向、不 flush，缓冲区内容会在**恢复 fd
     之后**才落盘 —— 重定向窗口"看起来"盖住了，实际全泄漏。
  2. 故必须**在恢复 fd 之前 flush**，否则静音无效（这是最初的 bug 根因）。
  3. 测本函数**必须开全新子进程**：同进程内若前面已裸跑过一次，
     那唯一一次打印已被消费，再断言"没看到提示"恒真 —— 空转断言。

  实测对照（`probe_silence_fix.txt`）：裸跑 `find_tables` 泄漏 = True，
  走生产路径 `locate_cells` 泄漏 = **False**。

- **多栏版面**：脱敏结果正确（按矩形处理，不依赖阅读顺序），
  但位置标签里不含栏号。
- **占位符可能改变版面**：占位符比原串长时会挤占相邻空白区域；
  窄框下 `insert_textbox` 会自动折行。
- **✅ PDF 元数据已清洗**（P3）：
  `/Info` 字典的 6 个可写字段（Title / Author / Subject / Keywords /
  Creator / Producer）与 **XMP** 包，均在本轮补齐。
  实测：`set_metadata(title="报告 13800138000")` 走一遍脱敏后，
  `fitz` 读 `metadata['title']` 已变为 `报告 [手机号]`；
  XMP 里的实体编码（`1380013&#56;000`）也能识别并清洗。
  位置标签形如 `元数据 /Title` / `元数据 XMP`，`page_index = -1`。

  **仍有边界，不静默漏掉**：
  - **XMP 跨节点敏感串**：手机号被 XML 标签拆开（`前13800` + `138000后`）时，
    任何单节点视角都识别不出。此时**报告会给出 ⚠️ 提示要求人工核查**，
    不假装已清洗。
  - **`/Info` 的其余字段**：`creationDate` / `modDate` 格式固定（规则不会命中），
    `trapped` 取值仅 True/False/Unknown，`format` / `encryption` **只读**改不动。
  - **另 5 处藏身处实测都含敏感串，首版不做**：书签、注释、链接、
    内嵌文件、表单域。**请人工核查这些位置。**

### 通用

- **规则型识别**：只认 YAML 里配置的格式。人名、地址、单位名一律不识别。
- **不做语义判断**：一串 16–19 位数字若 Luhn 校验通过就会被当成银行卡号；
  校验位只能过滤格式错误，过不了"语义是否合理"这一关。
- **字体表 `fontTable.xml` 中的字体度量值可能被误匹配为银行卡号**
  （例如 panose1 值 `0502020204030204` 形式上是 16 位数字）。
  但本工具**不读写该文件**，它会随原样保留在输出文档中，因此**无实际影响**。
  （由独立验证时发现并记录。）

### docx（P1 全通：优先级 1–6）

**已处理**：正文段落、表格（含嵌套）、页眉页脚（含首页/偶数页）、批注、文本框（含嵌套）、脚注、尾注。
跨 run、`<w:br/>`、`<w:tab/>`、`<w:hyperlink>`、拼写校对标记、书签均支持。

**未处理 / 会跳过的**（本版**不脱敏**，需人工核查）：

| 位置 | 说明 |
|---|---|
| **域代码 / 修订标记 / 图形对象** | 含这些结构时**只跳过该段落**，同容器其他段落照常处理 |

**批注的处理方式**（优先级 5）：

批注存在独立 part `word/comments.xml`，正文侧通过 `commentRangeStart` /
`commentRangeEnd` / `commentReference` 三个元素的 `w:id` 与之关联。

- **只改批注段落里的文本，绝不碰任何 `w:id`**——正文侧的关联完全依赖它。
  实测处理后 Word 能正常打开，批注数与作者均保留。
- **批注作者名（`w:author` / `w:initials`）不脱敏**。本工具不识别"人名"，
  纯正则无法可靠判断，强行匹配会误伤。若作者名本身填了手机号或邮箱
  （有些人用邮箱当署名），**需人工处理**。
- **带批注标记的正文段落也正常脱敏**。这三个标记元素是**无文本、不占偏移**的
  （与 `<w:br/>` / `<w:tab/>` 不同，后者各占1 个字符并参与偏移映射），
  因此放行后不影响匹配。早期版本因未放行，导致真实文档里所有带批注的段落
  被当作"复杂结构"整段跳过——这是已修复的真实盲区。

报告位置标签为 `批注 #<w:id>`（用文档内部唯一 id，比遍历序号稳定）。

**文本框/ 脚注 / 尾注的处理方式**（优先级 6）：

三类容器的存储形态完全不同，遍历方式各异：

| 容器 | 存储位置 | 备注 |
|---|---|---|
| 文本框 | `document.xml` 内的 `<w:txbxContent>` | VML 与 DrawingML 共用此元素；嵌套用递归（上限 5 层） |
| 脚注/ 尾注 | `word/footnotes.xml` / `endnotes.xml` | part **没有 `element` 属性**，须解析 blob 后**显式写回**，否则不落盘 |

- 脚注/尾注里的 `w:type="separator"` / `"continuationSeparator"` 是
  **系统保留条目**（分隔线用），按 `w:type` 过滤，不参与处理。
- `w:id` 是正文侧 `footnoteReference` / `endnoteReference` 的关联依据，
  **绝不修改**（已验证处理后 Word 脚注/尾注数与引用位置均正常）。

**拼写校对标记与书签**：`w:proofErr`（拼写/语法校对）与
`w:bookmarkStart` / `w:bookmarkEnd` 都是**空元素、不占偏移**，已放行。
这一点很重要——**Word 默认会自动插入 `proofErr`**，
几乎所有人工编辑过的文档都有；不放行会让大量段落正文整段跳过、漏脱敏。

**表格的处理方式**（优先级 3）：

`document.paragraphs` **不包含表格内的段落**，所以表格必须独立遍历
（`document.tables` → `rows` → `cells` → `paragraphs`）。三个关键处理：

- **合并单元格按 XML 元素去重**。合并后 `cell(0,0) is cell(0,1)` 是同一个
  XML 元素，若重复访问会**虚增命中次数**。
- **嵌套表格递归处理**（深度上限 5 层，防病态文档）。
- **跳过粒度是段落而非整表**：域代码通常只在个别单元格（如页码栏），
  整表跳过会连带漏掉同表其他单元格的敏感信息。

报告位置标签用 `表1 R2C3` 格式（紧凑、与 Word 界面一致），嵌套表为
`表3 R1C1 内表1 R1C1`。

**页眉页脚的处理方式**（优先级 4）：

页眉页脚存放在独立 part（`word/header1.xml` 等），`document.paragraphs` 不含它们，
因此独立遍历。两个关键点：

- **只处理实际存在的页眉页脚**。实现从 `sectPr` 的引用元素直读，
  **不碰 `section.first_page_header` 等代理属性**——实测读取那些属性会
  自动创建原本不存在的 part（凭空生成空页眉并在 `sectPr` 里加引用），
  等于改变文档结构。
- **按 part 对象本身去重**（不用 `id()`，见表格部分的同源教训），
  避免"链接到前一节"时被重复处理、虚增命中次数。

页眉内的表格与超链接同样处理（页眉 part 有独立的 `rels`）。

报告位置标签形如 `页眉 第1节`、`首页页眉 第1节`、`偶数页页眉 第1节`。
报告会提示：首页/偶数页内容**仅在文档开启对应设置时才显示**，
但本工具仍会一并脱敏——"处理了却看不到变化"属正常现象。

**br/tab 的处理方式**：这类元素在文本流里各占 1 个占位字符（`\n` / `\t`），
使偏移量与真实字符位置保持一致；替换时元素本身原样保留，因此换行、制表符不会被破坏。

> 注意：号码**本身**被换行拆开时（`1380013⏎8000`）**不会**被识别。
> 这是有意为之——跨行的数字串不构成有效手机号，强行匹配反而会误伤。
> 真实文档中不存在这种写法。

**超链接的处理方式**（优先级 2）：

Word 把超链接拆两处存放：正文存显示文字 + `rId`，**真实 URL 存在
`word/_rels/document.xml.rels` 里**。因此正文正则扫不到 URL——
`mailto:someone@company.com` 会原封不动躺在 rels 文件里。处理方式：

| 对象 | 处理 |
|---|---|
| 显示文字 | 按现有规则脱敏，占位符替换文字 |
| `mailto:` 目标 | 改写 Target 为 `mailto:[邮箱]`（`[邮箱]` 做 URL 编码） |
| `https://` 等其他目标 | **原样保留**（不含敏感信息） |
| 内部锚点（`w:anchor`） | 只处理显示文字，**锚点不动** |

改写 Target 时**不删除 Relationship 条目**——删除会让正文里的 `rId`
变成悬空引用，属于"Word 能容忍但结构已损坏"的坏数据。

**报告里的占位符是真实落盘值**：这类命中不对应任何一条脱敏规则（改的是
URL，不是正文文本），因此不能按规则名反推。报告会显示 `-> mailto:[邮箱]`
——与文档里实际写入的一致（`rels` 中为 URL 编码形式，报告展示解码后的可读值）。
若显示成 `[超链接目标]`，用户会误以为文档里写的是那个字符串，而事实并非如此。
实现见 `HitStat.placeholder_text` 字段。

**已知限制**：URL 路径中的其他敏感信息（query 参数里的 token、路径里的工号等）
本版**不脱敏**，因为没有统一的识别规则，贸然匹配容易误判。

**格式保留的三个要点**：

1. **占位符继承首个 run 的格式**。手机号原本拆成"加粗 + 斜体 + 常规"三段，
   脱敏后 `[手机号]` 显示为**加粗**（跟随首个 run）。
2. **未被命中的 run 完全不被触碰**，格式自然保留。
3. **被删空的 run 会从 XML 中移除**。跨 run 替换会让中间/末尾的 run 文本变空，
   若保留空壳，它在 Word 里是**零宽度**的——不渲染也选不中，
   用户会看到"格式似乎存在却点不中"的困惑。移除后空白自然并入相邻 run。

### xlsx（P2 全通 + P3 补 custom.xml 与数组公式）

**已处理**（v0.4.0 + v0.5.0）：
14 类容器 = 单元格（字符串/数值/公式）、批注、页眉页脚、工作簿属性、
定义名称、图表、隐藏工作表；外加 `docProps/custom.xml` 自定义属性、
数组公式（扫字符串清洗，结构保留）。

**未处理 / 会跳过的**（本版**不脱敏**或**数据丢失**，需人工核查）：

| 位置 | 说明 |
|---|---|
| **`xl/tables/tableN.xml` 整目录丢失**（v0.5 实测） | openpyxl 重写 xlsx 时会把整 `xl/tables/` 目录吞掉。**非漏敏**：源里所有命名表（含表名、表头、列定义）一并消失。这是**数据丢失**，不是漏敏——敏感信息不会被替换为占位符，而是原数据被丢掉。若用户原文件依赖命名表（如 Excel 数据验证下拉、引用查询），输出后请人工重建 |
| **`docProps/app.xml` TitlesOfParts 丢失**（v0.5 实测） | openpyxl 重写时 `app.xml` 的 `TitlesOfParts` 字段被简化（包含的工作表名/打印顺序/文档统计等元信息丢失）。**非漏敏**，仅 Excel 后台元数据损失，对内容无影响 |
| **共享公式主格（`t="shared"` 带 `ref=`）** | openpyxl 读入时会自动把共享公式的引用格展开为独立公式，故本工具**只按普通公式清洗**。真 Excel 直改 ZIP 文件时主格 + 引用格独立公式都能清洗，但经过 openpyxl 中转会被自动展平。攻击场景需人工核查 |

**xlsx 容器清单**（实测覆盖）：
单元格（含数值/字符串/公式）、批注（独立 part `xl/comments*.xml`）、
页眉页脚（openpyxl 高层 API，与 docx 类似）、工作簿属性（`docProps/core.xml`、
`docProps/app.xml` 的可写字段）、定义名称（`wb.defined_names`）、图表
（最后 save 后改 ZIP，因为 openpyxl 重写会丢图表关联）、隐藏工作表
（`state='hidden'` / `'veryHidden'` 同样按内容清洗，只是位置标签标"（隐藏）"）。

**两个特殊容器**：
- `docProps/custom.xml`：P3 走 `wb.custom_doc_props.props` 高层 API。
  StringProperty/LinkProperty 的 `name` 与 `value` 都跑引擎；IntProperty/
  FloatProperty 走数值路径（含超精度告警）；BoolProperty/DateTimeProperty
  跳过（无文本）。位置标签 `工作簿 自定义属性 {idx}`（**不带 name**，避免 name 本身含敏）。
- 数组公式：P3 改"跳过 + 告警"为"扫字符串清洗，保留结构"。
  用 `ArrayFormula(ref, new_text)` 重建，`ref="B1:B1"` 结构保留。

## 快速开始

```bash
# 看看内置了哪些规则
redactor rules

# 先看会发生什么，不写任何文件（推荐第一步）
redactor dry-run 待脱敏文件.txt

# 确认无误后正式执行，输出到 redacted_output/
redactor run 待脱敏文件.txt

# 批量处理整个目录，保留子目录结构
redactor run 待脱敏目录/ -r -o 输出目录/

# 只用指定规则 + 编号占位符
redactor run a.txt --only 手机号 --numbered

# 出一份 JSON 报告
redactor run 待脱敏目录/ -r --report 报告.json --report-format json
```

### 常用参数

| 参数 | 说明 |
|---|---|
| `-o, --output` | 输出根目录，默认 `redacted_output/` |
| `-r, --recursive` | 递归子目录 |
| `--only 规则名 ...` | 只启用指定规则 |
| `--numbered` | 强制编号占位符（`[手机号#1]`）。**默认关闭**：编号会暴露"这两处是同一个号" |
| `--report` | 报告另存为文件。**文本报告带 UTF-8 BOM**，Windows 下可直接 `type` 查看；JSON 不带 BOM |
| `--overwrite-output` | 允许覆盖已存在的**输出**文件（仍永不覆盖原文件） |
| `REDACTOR_RULES_DIR` | 环境变量，整体替换规则目录 |

### 报告的编码

`--report` 写出的**文本报告带 UTF-8 BOM**。原因是 Windows 的 `type` 命令、
记事本等按系统默认编码（简体中文Windows 为 GBK）解码无 BOM 的 UTF-8，
中文会显示为乱码；加了 BOM 它们就能正确识别。

**JSON 报告不加 BOM**——`json.load()` 遇到 BOM 会直接抛
`Unexpected UTF-8 BOM`，导致下游系统读取失败。程序侧已强制这一点：
即使内部参数请求加 BOM，JSON 路径也会忽略。

用 Python 读取带 BOM 的文本报告时请用 `encoding="utf-8-sig"`；
普通编辑器、VS Code、Notepad++ 均可直接打开，无需额外设置。

换行符恒为 LF，不随系统变为 CRLF。

### 退出码

| 码 | 含义 |
|---|---|
| 0 | 全部成功 |
| 1 | 有文件未能处理（详见报告「需要人工处理的文件」） |
| 2 | 参数错误或规则文件错误 |
| 130 | 用户中断 |

## 扩展规则

编辑 `rules/builtin.yaml`，或新建 `rules/myrules.yaml`（同一目录下的多个文件会按文件名顺序合并）：

```yaml
rules:
  - name: 内部工号
    description: 公司内部工号格式 EMP-12345
    pattern: 'EMP-\d{5}'
    placeholder: '[工号]'
    validator: null      # 可选：id_card / luhn
    flags: [IGNORECASE]  # 可选：IGNORECASE/MULTILINE/DOTALL/VERBOSE/UNICODE
    numbered: false      # true 则输出 [内部工号#1]
    enabled: true        # false 则本条不参与匹配（但仍会被校验）
```

**加载是严格的**：字段拼错、重复规则名、非法正则、非法校验位名——任何一处出错都会
报错退出并指出行号。这是刻意设计：静默跳过一条规则，等于给用户制造"已脱敏"的错觉。

## 自定义词库

除了正则规则，还可以维护一份**敏感词清单**，用于脱敏内置正则识别不出来的专有名词
（项目名、公司名、人名等）。

词库文件默认为 `~/.redactor/lexicon.yaml`，格式：

```yaml
lexicon:
  - name: 甲方单位            # 必填。占位符即 [甲方单位]
    words:                    # 必填，词条列表
      - 重庆某某水务
      - 重庆某某环保
    numbered: false           # 可选。**首版不生效**，见下
    note: 2026年框架合同甲方   # 可选，仅文档说明
    enabled: true             # 可选，false 则本条目不参与匹配（但仍会被校验）
```

**归一化**：加载时把全角转半角（`０-９Ａ-Ｚａ-ｚ` 与表意空格 `　`），
所以词库里写 `Ｇｏｏｇｌｅ` 能匹配文档里的 `Google`。
只做这两条 1:1 映射，**不做完整 NFKC 也不做简繁互转**——
前者会把 `Ⅳ`、`㍿`、`⑴` 展开成多字符，导致替换位置错位；
后者需要额外依赖。简繁请在词库里两种写法都写。

**去重规则**：
- 同一条目内的重复词 → **报错**并指出两行行号（这是笔误）
- 跨条目的重复词 → **静默去重**，保留首次出现（同一单位挂两个类别是正常用法）

**编号不支持**：词库条目的 `numbered` 字段首版不生效，
同一类别下的多个词统一脱敏为 `[类别名]`。若需要编号，请拆成多个条目。
理由：编号会暴露"这两处不是同一个单位"，本身就是隐私泄露。

**与正则规则的优先级**：词库条目一律排在内置正则之后。
同一起点冲突时内置正则胜出；但**词库条目的起点更靠前时会吃掉正则命中**
（消解按`start` 升序先到先得）。因此词条要写得精确——
例如不要写 `'联系人张三13800138000'` 这种整句，会连带吞掉手机号。

**条目名不得与内置规则同名**：两者占位符都是 `[名字]`，
报告会无法分辨命中来源，故加载时直接报错。

**匹配实现**：所有词库条目**共用一台 Aho-Corasick 自动机**，文本只扫一遍。
实测（300~5000 总词数）比"每个条目一个识别器"快2.9~7.8 倍，
且命中集合逐项完全一致。

**命令行用法**：

```bash
# 不指定：自动加载 ~/.redactor/lexicon.yaml，不存在则不启用（正常情况）
redactor run 待处理目录/

# 显式指定词库文件
redactor run 待处理目录/ --lexicon D://我的词库.yaml

# 明确禁用词库（即使默认词库存在也不加载）
redactor run 待处理目录/ --no-lexicon

# 查看当前生效的规则与词库条目
redactor rules --lexicon D://我的词库.yaml
```

行为约定：

| 情形 | 行为 |
|---|---|
| 显式 `--lexicon` 但文件不存在 | **报错并以非 0 退出**，不落盘任何文件 |
| 未指定、默认词库不存在 | 静默跳过（正常情况） |
| `--no-lexicon` | 明确禁用，连默认词库也不看 |
| 词库条目名与内置规则同名 | **报错**并指出行号 |

**词条内容绝不打印**：`redactor rules` 只显示条目名、词数、行号、备注，
不显示词条本身——词条就是敏感清单，打到终端或日志等于泄露。
报告同理（报告只记规则名、命中数与位置）。

词库相关测试合计 146 项（lexicon 77 + recognizer 50 + CLI 19）；
PDF 相关 **128 项**（含 L3 差分验证与反向对照、P2 表格分类、
**P3 元数据清洗 23 项**，以及 6 + 13 项变异实验）。

P3 元数据清洗的 23 项测试都遵循"正向 + 反向对照"成对出现：
凡断言"已清洗"，必配一条证明"清洗失效时确实能观察到残留"。
另跑了 **13 项变异实验**（把实现逐条改坏，确认测试真的会失败），
**13/13 全部被杀死**，证明这些断言不是恒真。
